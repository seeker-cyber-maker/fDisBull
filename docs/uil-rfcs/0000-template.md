## Semantic limitation

Describe the smallest behavior that current UIL cannot represent honestly.

## Motivation and evidence

Name the game family or workload, inspected evidence and exact limitation.
Keep proprietary bytes and host paths out of the RFC.

## Proposed semantics

Define state, operations, events, ordering, failure behavior and canonical
encoding. Specify numeric, time and random behavior where applicable.

## Capability declaration

State whether the feature is required or optional and how a consumer detects
support. Define fail-closed behavior for an unsupported required capability.

## Provenance and debugging

Explain how source maps, shared labels, traces and debugger observations attach
to the new constructs.

## Compatibility and migration

Explain how existing UIL retains its meaning and how an older consumer handles
the proposal.

## Security boundary

List permitted effects. Explain why the proposal does not introduce arbitrary
host code, filesystem, network or native-library execution.

## Conformance fixtures

Identify a redistributable synthetic fixture plus positive, negative and
malformed-input vectors.

## Alternatives

Show whether existing UIL could represent the game without this amendment and
why that option is inadequate or preferable.

## Implementation experience

Record producer and consumer prototypes separately. A successful prototype is
not by itself adoption evidence.

## Disposition

Maintainers record the adopted scope, evidence, open limitations and lifecycle
state here. Acceptance does not automatically enable an implementation or
qualify a game.
