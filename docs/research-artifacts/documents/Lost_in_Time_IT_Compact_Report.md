# Lost in Time — Italian compact media build

29 October 2026. This package contains a **40,343,552-byte data-only CD image**, tools to reproduce it from the supplied Italian release, the recovered media/container formats, and the validation evidence.

The main build replaces intermediate animation in **20 of 497 IMD movies** with valid native hold records. It preserves those movies' original frame counts and first/final images and palettes. The other **477 movie members are byte-identical** to their originals. It also omits the original disc's separate CD-audio track. The original executable and localized text resources are unchanged.

The original DOS executable boots with the compact ISO mounted as a CD, and the tested opening interaction works in Italian. All 20 modified movies separately passed complete decoding and endpoint comparison. This is an opening smoke test plus media validation; it is not a complete-game playthrough.

All relative paths below refer to files inside this package. The original uploads and the earlier continuation package were not modified.

## Run the supplied build

The ISO, Python preparation tool and Italian configuration are included. A DOSBox-compatible emulator is required separately. The actual native comparison used the fDisBull 0.22.0 DOSBox backend; that large backend and its Python environment are not duplicated here.

From the extracted package directory, run this with Python 3 (the preparation and rebuild tools were tested with Python 3.12):

    python3 prepare_game.py /absolute/path/to/new/LostIT

Choose a new directory. The tool extracts the ISO's 26 files and adds the Italian MDO.CFG generated by the game's own SETUP.EXE. It prints the exact DOSBox commands for your paths:

    mount c "/absolute/path/to/new/LostIT"
    imgmount d "/absolute/path/to/Lost_in_Time_IT_Framed.iso" -t iso
    c:
    lost.exe

The executable and game data run from the writable C: copy, with the ISO mounted as D:. This is the arrangement tested. The virtual CD mount is still required: a directory-only launch requested a CD-ROM. The CD installer and direct execution from the ISO were not qualified. No executable patch was needed.

The supplied configuration selects Italiano. Keep the ISO available after preparing the directory. Preparation refuses an existing destination so it cannot overwrite saved progress.

## Measured sizes and content changes

MB here means decimal megabytes. Byte counts are the authoritative measurements.

| Object | Bytes | Meaning |
|---|---:|---|
| Supplied Italian ZIP | 525,176,084 | Original compressed download |
| Original mixed-mode BIN | 607,509,840 | Raw data sectors plus CD audio |
| Original CD-audio payload | 558,821,088 | Separate track; 3,167.92 seconds |
| Original cooked data ISO | 41,930,752 | Original filesystem, without CD audio or raw-sector overhead |
| Original 26 file payloads | 41,861,870 | Files inside that filesystem |
| Framed 26 file payloads | 40,274,658 | Rebuilt paired resource archives, other files unchanged |
| Supplied framed ISO | **40,343,552** | Compact data-only virtual CD |

**Video framing saves 1,587,212 bytes of game-file data, or 3.79%.** ISO sector rounding makes the corresponding image saving 1,587,200 bytes. The much larger reduction from the original BIN is chiefly removal of the separate audio track, which accounts for 91.99% of that BIN; removing raw-sector overhead and unused space also contributes. The 93.36% raw-image reduction must not be described as video compression.

The CD-audio content is omitted, not assumed to be music-only. The compact ZIP's measured download size is reported separately at delivery; it includes the ISO, tools, examples and evidence. A prepared game directory also contains the 41-byte Italian configuration. Keeping both that directory and the ISO uses roughly twice the data-image space.

The movie manifest identifies every changed and preserved member, original and new lengths, retained frame indices, and the reason for each preservation. There are **288 logical frames** across the 20 changed clips; **246 record positions** are replaced by native holds. Frame numbering remains intact, so this method reduces payload without necessarily shortening the wait during an animation.

## The format work that makes this possible

The media path is ISO9660 files → paired ITK/LTK resources → IMD movies. Each layer has lengths and positions that must remain consistent.

| Layer | Recovered structure | Rewrite obligation |
|---|---|---|
| IMD | Frame count, geometry, palette, variable header, frame packets, optional absolute position table | Retain a complete stream and rebuild its count/index/pointer fields |
| ITK | Count followed by 22-byte name/size/offset/packing entries; even-aligned member payloads | Recalculate changed sizes and all shifted member offsets |
| LTK | Cached IMD headers, native frame indices, complete frame boundaries, member positions and per-frame bytes | Rebuild together with ITK; an ITK-only rewrite leaves stale metadata |
| ISO9660 | Directory records, file extents and volume length, with little- and big-endian fields | Relocate files, update both endian copies and verify every payload |

The key extra discovery is **LTK**. Its records cache much of the IMD structure, so a standalone shortened movie that decodes correctly is not sufficient for a valid game archive. The variable-record equation accounts for every one of the 497 original members:

    32 + header_size + 4*indexed_count + 4*(frame_count+1) + frame_count

The final term is an opaque per-frame byte array. Its general algorithm remains unresolved. This writer retains the byte associated with an exactly retained original packet. For an exact two-byte 00 00 hold, it writes 02: that mapping occurs in all **703 genuine hold records** found in the original assets. It refuses new nonmatching encoded packets rather than guessing that field.

The actual media contains 490 version-4 IMDs and seven version-2 IMDs. None of these members uses the embedded-sound or per-frame-coordinate-table features. The main build keeps all seven version-2 members unchanged. It also preserves two unexplained originals: INV5.IMD has an unknown footer, and PRECIP4.IMD has an irregular indexed media region.

The detailed byte maps and source provenance are in [research/IMD_Format_and_Truncation.md](research/IMD_Format_and_Truncation.md) and [disc/Disc_Format_Findings.txt](disc/Disc_Format_Findings.txt). The parser retains unknown header padding; unexplained tails, layouts and unsupported features are refused for rewriting.

## Framing and literal truncation

The main transformation retains the first frame, finds the last independent full-frame packet, and retains that packet and every following delta frame. The interval between them becomes native two-byte holds. It then rebuilds the IMD index and both resource containers. Retaining the final whole packet together with its delta tail avoids treating a dependent delta frame as a standalone final image.

The selection profile limits this to long full-scene candidates with no standard-coordinate subrectangle. Known interactive movies, inventory/subrectangle graphics, short assets, version-2 members and anomalous layouts remain unchanged. This is a conservative heuristic, not a proof that the remaining candidates are never accessed at intermediate frame numbers.

The supplied DESCC example shows the distinction:

| Variant | Bytes | Logical frames | Use |
|---|---:|---:|---|
| Original | 364,749 | 25 | Reference |
| True one-frame prefix | **12,888** | 1 | Independently decoded format demonstration; not in the ISO |
| Framed version | **24,864** | 25 | Deployed in the ISO; matching first/final pixels and palettes |

The prefix removes 96.47% of this movie's bytes. The framed version removes 93.18%. A true prefix is valid IMD media, but changes script-visible frame ranges and the ending image. The main build therefore uses framing.

To make new standalone examples without altering the included files:

    python3 imd.py inspect examples/DESCC-original.IMD
    python3 imd.py prefix examples/DESCC-original.IMD my-prefix.IMD --keep 1
    python3 imd.py frame examples/DESCC-original.IMD my-framed.IMD --keep 1

The additional hold-tail mode preserves frame count but discards the ending image; it is a diagnostic option, not the chosen build profile.

## What was verified

**Containers and files.** All six unchanged ITK/LTK pairs round-tripped byte for byte. The unchanged ISO also round-tripped exactly. Rebuilt pairs reparse, and the final ISO's 26 payloads match their selected source or replacement files. The unchanged serialization check passed for 495 regular IMDs; the two irregular originals are preserved.

**Media decoding.** A separate C++17 decoder, based on pinned ScummVM algorithms, fully decoded each original and modified member in the 20-movie set. Every indexed boundary was checked. All first/final pixel buffers, first/final palettes, frame counts and geometric metadata matched, with zero differing endpoint bytes. It decoded 481 original movies in the wider survey; the other 16 are explicit scope refusals, not new corruption. Its source, Linux executable, license and reports are included under research/decoder/.

**Original runtime.** fDisBull 0.22.0 controlled the original DOS executable with each data-only ISO mounted. The same original SETUP-generated Italian configuration was used in both runs. Five captured screenshots match byte for byte, including the opening bucket interaction and Italian text. Both processes closed and were reaped. See [runtime-test/Native_Runtime_Comparison.md](runtime-test/Native_Runtime_Comparison.md).

The runtime smoke test has no file-access trace proving that one of the 20 altered movies was consumed. It establishes boot, archive acceptance, Italian configuration and opening interaction. Complete decoding of the modified movies is established separately by the C++ comparison. Intermediate images intentionally differ; direct seeks into removed animation and full-game puzzle behavior have not been qualified. CD-audio playback is absent from this build.

## Reproduce from the supplied Italian archive

All output directories in this example must be new. The extraction streams the data volume without expanding the large audio tail. Python tools use the standard library.

    python3 disc/extract_cd.py /path/to/Lost-in-Time_DOS_IT_ISO-Version.zip rebuilt-source
    python3 build_video_rip.py rebuilt-source/original-data rebuilt-data --report rebuilt-manifest.json
    python3 disc/repack_iso.py rebuilt-source/original-data.iso rebuilt-data rebuilt-disc

The result is rebuilt-disc/LostIT.iso. The selection logic is in build_video_rip.py; the exact deployed choices are in framing-manifest.json. To repeat the independent media comparison:

    g++ -std=c++17 -O2 -Wall -Wextra -Werror research/decoder/imd_reference.cpp -o research/decoder/imd_reference
    python3 research/decoder/compare_framing.py --manifest rebuilt-manifest.json --original-dir rebuilt-source/original-data --modified-dir rebuilt-data --report rebuilt-endpoints.json

Existing evidence JSON retains the absolute paths from the original experiment as provenance. Rebuild commands use your own new paths. The optional runtime driver accepts an explicit --backend path; its README section explains the external fDisBull dependency.

The disc tool also exposes an optional same-duration silent WAVE/CUE mode. It is not part of the supplied ISO. Silence keeps a large logical PCM file even if it compresses well, so it is a distribution-size alternative, not the same installed-size saving. Original-duration audio timing and its proposed CUE layout have not been qualified by native playback.

## Historical basis and continuation

The period term is movie framing. The surviving March 2004 Standard Rip Rules explicitly discuss it; the history note separates that dated evidence from 1990s tooling and later catalogue mentions. This is an implementation inspired by documented techniques, not a claim to reproduce a particular group's Lost in Time release. See [history/Historical_CD_Rip_Methods.md](history/Historical_CD_Rip_Methods.md).

[Knowledge_Pack.txt](Knowledge_Pack.txt) records the executive summary, architecture, decisions, completed tasks, research, remaining questions, continuation memory and next steps. Further reductions should follow script frame-use evidence or recovery of the general LTK per-frame-byte algorithm. Neither is required to reproduce this bounded build, and neither has been claimed solved.
