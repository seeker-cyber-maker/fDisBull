# Reuse XCOM startup, state and event-discovery work

Decision: 18 November 2026. XCOM is another existing research source for DotBox's
bootstrap and process model. Recover its named controls, serializer experiments,
visual recognition and event-discovery work before repeating them. Original
Cryo Dune remains the next selected transfer target; this map does not schedule
a new XCOM playthrough or port a provider.

Status: read-only recovery of public authored material and source. No new XCOM
execution, complete loop model or DotBox XCOM harness is established here.
The general operating direction is [bootstrap and event loops](BOOTSTRAP_AND_EVENT_LOOPS.md),
packaged as `loops`; this reuse map is `dotbox guide --topic xcom`.

## Save/load and state lessons

One prepared serializer trial followed menu selection, slot selection, a bulk
loader and per-file read/apply routines. Other UI or assisted runs observed
changed funds and restoration. In a later cold native-contract attempt, altered
bytes reached a sampled destination buffer, but whole strategic loading and
refreshed funds were not achieved; a later direct reader replay failed at open.
The successful captured transfer remains evidence even though the larger goal
failed. Exact restoration of a disk file alone did not establish live restoration.
Do not borrow success from another prepared run to close that cold attempt. [X1, X3]

Retain each operation's request/selection, file and buffer effects, authoritative
adoption, original continuation/initialization, presentation and readiness. Their
relationships are action-specific. Keep the attempt and ask what boundary is
still missing; do not automatically click Load or submit a transaction again.
The proposed DotBox process model needs these distinctions without importing the
entire UDL/UIL/UDC stack.

For [alternative entry routes](BEHAVIOR_AND_ENTRY_POINTS.md), name the boundary
actually invoked. A low-level file reader, a bulk loader and the wrapper that
selects a slot, adopts state and continues the interface have different contracts.
Recover original setup and continuation instead of assuming a call to the reader
is equivalent to selecting Load. Deeper routes can accelerate isolated research
once their selected effects and required context are established; the ordinary
menu route remains a usable fallback.

Source identity also matters: a strategic slot, mission handoff, live tactical
screen and numbered tactical save are different artifacts. The reported 250
soldier positions are record positions, not proof of 250 active soldiers.
Candidate name joins and strides are useful structural leads, not complete
cross-context identity or field semantics. [X1, X3]

## Discovery captures and inexpensive routine recognition

The visual workflow uses full observation for discovery/unfamiliar states, then
qualified stable discriminating samples for routine checks. Reserve anchors,
negative checks and coherent context protect against accidental matches. A
classifier or local vision proposal does not authorize its own acceptance. [X4]

The 7 November original-menu note reports four fresh UFO navigation actions and
four Ultima local/navigation/mixed-effect actions, with zero routine screenshot
calls after qualification. Collection including setup used 495 UFO and 356
Ultima sparse probes; no minimal-polling or speedup result was claimed. UFO's
background appeared before its controls. Intermediate frames stayed unknown or
in the source context; an unregistered globe reached from an apparently blank
load row was not counted as successful loading. [X5]

That same note describes a shared `selector-controls-operation` structural scan:
scalar comparison, conditional arm and first call/write/return. It found 481 UFO
GEOSCAPE and 556 TFTD GEOSCAPE **source-arm candidates**, with instruction-budget
frontiers. These are not counts of buttons or automatic named-button discovery.
TFTD received static results only in that note. General delayed producer/consumer,
callback, queue/latch and native-to-script joining remained future work. [X5]

This is a precedent for [transition-family discovery](EVENT_TRANSITIONS.md):
recover one selector mechanism, enumerate related source bindings, then use
their differences and dependencies to direct further analysis. Menus are one
application of the shared event/guard/effect contract. Keep family-level facts,
binding semantics and current live applicability separate, and reuse established
common evidence without repeating an identical investigation for every candidate.

## Timing evidence does not define one XCOM preparation time

The user's ten-minute concern is a useful planning warning. It is not an observed
minimum, and displaying Geoscape does not establish understanding its game loop.
The retrieved reports explicitly distinguish fresh agent context from cold
tooling or absence of assistance. Preserve that distinction. [X1, X2]

| Historical experiment | Recorded milestone | Interpretation |
| --- | --- | --- |
| Earlier assisted UFO crossover | Title 14m47s-15m41s; requested usable base 21m24s-29m13s | Gross dispatch clocks for different assisted task bundles |
| Later UFO feedback retest, cold context | Title 90.457s; Geoscape 171.355s; requested full save/money goal still incomplete at 91.060 minutes | Early interface progress and difficult unfinished state-operation work in one run |
| Later TFTD feedback retest, cold context | Geoscape 268.551s; wrong requested region selected | Arrival alone did not satisfy the goal |
| Prepared new-game macro | 10.090s macro; 12.705s process start to Base Info | Retained-route replay, not cold learning |
| Prepared serializer trial | 40.389s restore sequence; 279.143s report completion | Prepared bindings, not independent calling-convention recovery |

No general speed comparison follows from those unlike conditions. None of the
retrieved material qualifies a complete original XCOM event loop or a standalone
DotBox harness. Measure first visibility, first useful action, the current
operating slice, relevant phase/clock coverage and complete requested outcome
separately. Persist the useful subset and qualify warm reuse independently.

## Transfer to DotBox in a small slice

1. Recover the exact compatible source/profile for one menu action and its
   observation predicates. Audit integration rather than assuming an MR note
   means every feature is present in the current package.
2. Bind selection, input attempt, effect, context and readiness to a coherent
   observation through DotBox's supported owner. Keep local mutation and
   navigation independent; retain unknown destinations.
3. On an isolated helper, compare repeated action A with idle/contrast B and
   inspect the smallest useful dispatch or deferred producer/consumer relation.
   Confirm executable mode and backend support before selecting trace primitives.
4. Return a source-bound model finding and a cheap applicability predicate.
   Check the live state before adopting it; helper state is not player progress.
5. Test one deferred effect or loader-adoption boundary. Keep confirmed partial
   effects and explicit continuation rather than repeating an accepted input.

The native package already exposes primitives and the inspected fDisBull source
contains generic event-search and serializer machinery. A qualified DotBox-owned
capture/adapter and phase-model store still need implementation. No player should
need an external fDisBull installation to use the eventual packaged capability.
