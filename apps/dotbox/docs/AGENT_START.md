# DotBox: keep the next interaction playable

DotBox is for playing the original graphical game with the user. The player
should not need to know about harnesses, debuggers or the learning machinery.
Dot is their conversational interface: describe the scene, offer useful choices
and carry out their intent. Autonomous play uses the same model within a
delegated goal. Description length, decision maker and hints are independent.

## Start with the useful action

Establish the installed runtime and supported input owner once. `dotbox doctor`
checks the offline learning kit; it does not establish live game readiness or
grant input. In default desktop mode, use the supported outer desktop tools.
Native `act`, key, click, play and pause RPCs require explicit diagnostic mode
and are refused in normal mode.

When the current observation and a known applicable control suffice for the
player's selected intent or delegated goal, act now.
Observe the result, then save any useful control metadata without repeating the
input. A scene name, wrapper or complete harness is not required before using
visible menu controls or otherwise applicable ordinary movement. Scene-specific
coordinates and state assumptions still need a fresh applicability check.
If a player-led choice is still open, present a few grounded options and wait
for intent; do not take the decision merely because its input is available.

Include a small initial manual/guide pass for the overall goal and controls,
then compare two or three compatible guides when useful and available. Their
objects and exits become expected checks. Observe which are actually present;
continue useful play with a partial scene. Guide-only objects and hidden
contents do not enter current narration. The run is guide-informed, even when
the player receives spoiler-light descriptions.

## Learn one missing interaction

Keep only the current goal, observed context, one operational question, immediate
next interaction and usable fallback in the active play context. Examples:
"Does Enter select this item?" or "Does releasing Right stop movement?" Retain
broader entities, relationships, rules and hypotheses in Dot's internal model;
a z-scene projects the relevant current view. Cheap whole-resource compilation
can run once and be cached without requiring exhaustive recovery before play.

Use `dotbox learn` when a missing control genuinely blocks progress. Its default
trial allowance is 15 seconds and two probe admissions. The clock includes time
between calls; reopening the same context does not reset it. On exhaustion,
use an applicable fallback or briefly explain the actual game-facing block.
Retire old work explicitly after a real player choice or context change. Never
rename an unchanged question to restart its allowance. The journal cannot stop
running tools, certify an outcome or grant input permission.

Reuse compatible knowledge first. Use visible controls, supplied instructions
or a bounded frozen-file inspection when sufficient. `dotbox inspect` provides
executable/resource hashes, strings, byte patterns, x86 windows and byte diffs.
These tools do not touch a live guest. Do not hold a game paused while reasoning,
reading files, authoring metadata or waiting for a worker. Qualified live capture
must resume the guest before analysis; no general live capture facade ships yet.

For native/menu-driven work, consult `dotbox guide --topic dinopark` before
rediscovering state meanings or transaction behavior. Its prior mechanics
research and fDisBull provider supply reusable contracts. Rebind to the actual
edition and current observation; an old rule, supported verb or completion
receipt does not itself enable an action now. `dotbox guide --topic xcom` adds
the prior startup, serializer, event-discovery and sparse-recognition work.
Use `dotbox guide --topic loops` when the missing question concerns an intro,
menu, delayed operation, simulation phase or timer. Helpers can compare isolated
save/state variants while Dot follows the player's route; their findings are
knowledge, not live progression.

Use `dotbox guide --topic entrypoints` to reason from plausible code toward a
discriminating probe and a qualified alternative invocation. Preserve arguments,
setup, continuation and the exact effects shared with the original route.
An observation hook is not automatically callable. Isolated research can grow
from normally verified coordinates to coherent placement, original room entry
or direct menu operations; retain imposed-state provenance and normal fallbacks.

That guide also describes multi-probe control surveys: arm candidate sites,
record one control's transient hits, then restore a comparable isolated memory
baseline and re-arm for another. Retain the dispatch map before explaining every
handler. A first-hit stop truncates the rest of the path; missing observations
stay unknown. Preserve recordings across rewind and account for file effects.

For a confirmed compatible AGI V2/2.917 edition, `dotbox agi inspect` supplies
ordered logic conditions, state writers and resource candidates without general
x86 analysis. Cache a bounded whole-resource outline or resolve pass when its
cost fits preparation; deepen unresolved semantics along the useful frontier.
Save-file differences are useful state clues, not automatic semantic
labels. Use repeated baseline saves and one controlled action before interpreting
a difference. These tools do not refresh live flags or bypass the learning bound.

Keep reverse engineering available after preparation and for non-AGI games.
An ambiguous fact or missing relation can require native/resource analysis,
cross-context readers/writers or a qualified runtime capture. Distinguish one
persistent variable used elsewhere from one storage slot reused for another
meaning. Cache evidence-backed findings in the model. Raw native debugger
primitives are not yet a general owned live capture workflow in this package.

For supplied qualified geometry, `dotbox route` proposes shortest walking routes
with fewer turns and long straight legs. Execute through an applicable monitored
control only; a plan does not move the actor. Approach an exit before a separate
selected crossing, and rebind after transitions. Visible ordinary travel uses
original monitored movement. Coordinate placement is a separate research
capability, not evidence of having walked that route. Keep holds interruptible.

Optional improvements cause no intentional gameplay wait when a working route
exists. The 180-second initial-control profile is a ceiling for that job, never
a minimum wait, a universal game-loop recovery limit or an allowance to restart
in each room. A complex cold-preparation job can declare a longer bound and
milestones while retaining original elapsed time and misses. It cannot extend
the blocked foreground allowance. Start useful play as soon as supported.

## Retain progress

Separate candidate findings from observed effects. Accepted input alone does
not prove progress. Save evidence references and immutable control revisions;
keep the working revision until a compatible improvement is ready. Saving is
metadata work, never a reason to replay input. After uncertain partial effects,
observe before deciding whether to retry. After human play, refresh the actual
state and retire stale intentions; do not restore an old state to fit a recipe.

Retain provider-reported flags and inventory with their observation revision,
including confirmed offscreen effects. Keep historical values separate from
current reports, and use stable entity identities for objects shared across
rooms. Closed/open and locked/unlocked are independent; missing lock evidence
stays unknown. Recheck enabled actions and input readiness after changes, omit
completed actions from suggestions, and leave incidental commands available on
request. A response message does not itself prove a committed flag or readiness.
Conversational `look` describes known current facts without sending game input.

When usage permits, Dot can spawn full cloud agents to prepare the selected
destination and likely accessible next scenes. Workers consume frozen evidence
or their own isolated guest and edit separate candidates. Start appropriate
known movement promptly; actual travel gives workers useful preparation time.
Do not slow movement or stretch narration to hide missing work. Refresh on
arrival and adopt compatible candidates between actions. The 15-second journal
is the foreground missing-control allowance, not the background worker deadline;
neither arrival nor a late result resets an existing focus. One lead remains a
usable fallback when cloud workers are unavailable.
Keep player communication about the current game and consequential choices.
Keep original games, captures, stores and saves private.

Recovery from being stuck or a collision should use a qualified checkpoint or
game save. Restoring creates a new timeline and invalidates old choices, routes,
held input and worker candidates. Memory revert keeps current files on disk;
do not replace a save with an older copy to implement it. Preserve the player's actual progress after
takeover; rewind is a recovery action, not a way to make old assumptions fit.
DotBox has not yet exposed a fenced live restore command; consult the recovery
guide before adapting the native primitive.
